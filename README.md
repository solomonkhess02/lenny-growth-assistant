# The Lenny Growth Assistant

A conversational assistant over [Lenny's Podcast](https://www.lennysnewsletter.com/podcast)
transcripts. It answers product and growth questions **only** from what the transcripts actually
say, cites the episode and timestamp behind every claim, and turns a verified answer into a
Ship 30 for 30–style essay rendered beside the chat in an Artifact Viewer.

The organising property is trust: **every generated answer is mechanically verified against its
evidence before it is presented as an answer**, and one that fails is struck through and retracted
rather than footnoted. There is no configuration that turns that off.

Runs entirely on your machine — local models through Ollama, PostgreSQL in Docker. A cloud
provider (DeepSeek, via the Anthropic-compatible endpoint) is available per session and is never
substituted in silently.

![A grounded answer: evidence with episode timestamps above the text, inline [E1]/[E2] citations,
and a verified verdict below it](docs/screenshot-chat.png)

<sub>A real answer on local `qwen3:4b-instruct` in 27.7 s. Evidence renders **above** the text
because it was retrieved, not claimed; the verdict renders **below** because verification cannot
precede what it verifies.</sub>

## Quick start

Five commands. Detail for each is below; the two easy-to-miss ones are **Ollama runs on your host,
not in Docker**, and **ingestion is a separate step that needs network once**.

```bash
cp .env.example .env                       # defaults work as-is for the local path

ollama serve                               # in its own terminal, and keep it running
ollama pull qwen3:4b-instruct              # generation model (~2.5 GB)
ollama pull all-minilm                     # embedding model (~45 MB)

docker compose up -d                       # db + api; migrations run on API start
docker compose exec api python -m app.ingest   # ~50s, needs network once
```

Then open **<http://localhost:8000>** and ask something the podcast covers, for example
*"How does Duolingo use streaks to improve retention?"*

Expect a first local answer in roughly 25–40 s on modest hardware. It is generated by a 4B model on
your own GPU — it is not fast, and that is the trade-off of the mandated local path.

## Architecture overview

One FastAPI process serves both the JSON API and the built React app. Each layer below owns
exactly one concern, and the arrows are the only paths that exist:

```
routers/chat.py     transport only — SSE framing. No queries, no provider decisions.
  repository.py     all persistence; session-scoped by construction
  agent.py          orchestration
    retrieval.py    a database query, NOT an agent tool
    providers.py    the provider seam
      pi_runtime.py Pi Coding Agent as a subprocess, JSON-lines events
    grounding.py    quote and citation verification
  ship30.py         essay generation — content transformation, a separate path
  artifacts.py      the only place untrusted Markdown becomes HTML
```

Two invariants are structural rather than prompted, which is why they cannot be argued away by a
model:

- **No evidence, no answer.** When retrieval returns nothing, the model is never invoked at all.
  Abstention is a module constant, not an instruction the model may decline.
- **Every answer is verified.** `verify_answer` runs on all generated output, unconditionally —
  not gated on provider, model or configuration.

Retrieval is exact (`ORDER BY embedding <=> query`, no ANN index, 100% recall by construction)
with a total tie-break, so the same question returns the same evidence every time.

Full detail — schema, all 18 endpoints, ingestion flow, agent routing, security, deployment
topology — is in **[architecture.md](architecture.md)**. Product reasoning is in
**[PRD.md](PRD.md)**; interface decisions are in **[design.md](design.md)**.

## Prerequisites

| Requirement | Why | Notes |
|---|---|---|
| Docker + Docker Compose | Runs the API and PostgreSQL | Docker Desktop on Windows/macOS is fine |
| [Ollama](https://ollama.com), installed **on the host** | The mandated local model path | Deliberately **not** containerised — GPU passthrough on Windows/WSL2 is fragile |
| ~4 GB VRAM (or patience) | `qwen3:4b-instruct` at an 8,192-token context | Measured: 8192 → 4.1 GB / ~33 s per call. See the context note below |
| ~6 GB free disk | Images, models, database volume | |
| **Network access, once** | The transcript corpus is fetched at ingest time, not vendored | After ingestion the app runs fully offline |

**Why the corpus is not in the repo.** The upstream transcript archive carries no licence and this
repository is public, so instead of redistributing it,
[`manifest.json`](backend/app/corpus/manifest.json) pins identity (source commit + slug) and
integrity (a sha256 per episode), and ingestion downloads into git-ignored `data/transcripts/`,
**refusing on a hash mismatch** rather than indexing unverified content. A fresh clone therefore
has zero transcripts until you run the ingest step.

## Installation

### 1. Configuration

```bash
cp .env.example .env
```

The defaults are the local path and work unchanged. `.env.example` documents every variable inline,
marked REQUIRED or OPTIONAL, with the measurement behind each non-obvious default. You only need to
edit it to use the cloud provider, or if host port 5432 or 8000 is already taken.

### 2. Ollama, on the host

```bash
ollama serve                     # keep this running in its own terminal
ollama pull qwen3:4b-instruct
ollama pull all-minilm
```

**Set the context length before starting the server** — it is read by the Ollama *server* at
startup, not by this application:

```bash
# Linux / macOS
OLLAMA_CONTEXT_LENGTH=8192 ollama serve

# Windows PowerShell
$env:OLLAMA_CONTEXT_LENGTH = "8192"; ollama serve
```

8192 is a deliberate ceiling, not a default left alone. Measured on a 4 GB GTX 1650: **8192 →
4.1 GB VRAM, ~33 s per call; 32768 → 8.0 GB, ~173 s**. Raising it on a small GPU makes the app
appear to hang rather than fail.

### 3. Start the stack

```bash
docker compose up -d
```

This starts PostgreSQL (with pgvector) and the API. Database migrations run automatically in the
API entrypoint — there is no separate migration step. The API is healthy when:

```bash
curl http://localhost:8000/api/health
```

reports `"database":{"ok":true}` and `"provider":{...,"reachable":true,"model_available":true}`.
A reachable-but-unstarted Ollama shows as `degraded` (HTTP 200) rather than `unhealthy` (503),
because an operator needs to tell a broken deployment from an unstarted dependency.

### 4. Ingest the transcripts

**This does not happen automatically.** It is explicit on purpose: doing it at boot would make
`docker compose up` slow and would tie API liveness to the embedding model.

```bash
docker compose exec api python -m app.ingest
```

Takes roughly 50 seconds and ends with a summary line:

```
ingested=20 skipped=0 failed=0 total_chunks=1395
```

Verify:

```bash
curl http://localhost:8000/api/retrieval/status
# {"transcripts":20,"chunks":1395,...,"compatible":true,...}
```

Re-running is idempotent — unchanged episodes report `skipped=20` and are not re-embedded. Useful
flags: `--force` (re-ingest regardless of content hash), `--slug <name>` (one episode),
`--limit N`.

### 5. Use it

Open **<http://localhost:8000>**, click **New session**, choose a provider, and ask a question.

Ask something outside the corpus — *"How do I make a sourdough starter?"* — and the assistant will
say the transcripts do not support an answer instead of guessing. That is the system working.

## Environment variables

`.env.example` is the reference and documents each variable at its definition. The essentials:

| Variable | Required | Default | Notes |
|---|---|---|---|
| `LLM_PROVIDER` | ✅ | `ollama` | `ollama` or `deepseek`. Also the default offered in the UI |
| `OLLAMA_BASE_URL` | ✅ (local) | `http://127.0.0.1:11434` | **Use `127.0.0.1`, not `localhost`** — see Troubleshooting |
| `OLLAMA_MODEL` | ✅ (local) | `qwen3:4b-instruct` | Must be pulled first |
| `OLLAMA_CONTEXT_LENGTH` | ✅ | `8192` | Read by the Ollama server, not by this app |
| `EMBEDDING_MODEL` / `EMBEDDING_DIM` | ✅ | `all-minilm` / `384` | Changing either **requires a full re-ingest** — vector spaces are not interchangeable |
| `DEEPSEEK_API_KEY` | ✅ (cloud only) | — | Never commit it. `.env` is git-ignored |
| `DATABASE_URL` | ✅ | Compose supplies it | Inside the network the host is always `db:5432` |
| `POSTGRES_PORT` | ⬜ | `5432` | The published **host** port. Change if 5432 is taken |
| `GENERATION_IDLE_TIMEOUT_S` | ⬜ | `120` | Fires when a provider goes quiet mid-turn (primary bound) |
| `GENERATION_TIMEOUT_S` | ⬜ | `900` | Total wall-clock backstop per turn |
| `RETRIEVAL_MIN_SIMILARITY` | ⬜ | `0.40` | **Calibrated.** Changing it invalidates the frozen eval set |
| `LOG_LEVEL` | ⬜ | `INFO` | Structured JSON logs |

> **One trap worth knowing.** `.env` is `.dockerignore`d, so the container never reads it —
> Compose passes variables through explicitly. `RETRIEVAL_K`, `RETRIEVAL_MIN_SIMILARITY`,
> `RETRIEVAL_MAX_PER_SOURCE`, `ESSAY_RETRIEVAL_K`, `DEEPSEEK_MAX_TOKENS` and
> `DEEPSEEK_DISABLE_THINKING` are **not** forwarded. Tuning those in `.env` changes a host-side run
> only; the container keeps the `config.py` defaults. To change them for the Docker path, edit
> `docker-compose.yml` too.

Secrets are never logged or returned over HTTP: `/api/config` reports
`deepseek_api_key_present: true|false`, never the key itself.

## Local and cloud model setup

**Provider is chosen per session and is immutable.** It is selected when you create the session,
stamped on the row, and used by every turn in it. There is no PATCH endpoint and no provider field
on a message. Switching providers means starting a new session — which is what makes the stored
provider a true record of what produced each answer rather than a snapshot of whatever
configuration happened to hold later.

### Ollama — local, mandated demo path

Covered above. No API key. This is the path the demo runs on.

### DeepSeek — cloud

```bash
# .env
DEEPSEEK_API_KEY=sk-your-real-key
DEEPSEEK_MODEL=deepseek-v4-pro
```

Restart the API (`docker compose up -d api`) and pick **deepseek** when creating a session. It is
markedly faster for a grounded answer (measured in-container: **15.7 s**, against **28.9 s**
measured in-browser on local Ollama) and, being a far larger model, produces Ship 30 essays that
pass verification — which the local 4B model does not reliably do (see below).

### Fallback behaviour — there is none, deliberately

If a session's provider is unavailable, the turn ends in a structured error naming that provider,
and **nothing is switched for you**. A silent fallback would mean the provenance stamped on the
answer was a lie, and the retry button deliberately reissues on the same provider. This is
asserted by test, not merely documented: `test_a_failing_provider_is_surfaced_never_substituted`.

### Known limitation, measured and reported

**Ship 30 essays generated on `qwen3:4b-instruct` do not pass grounding verification.** At n=3 per
question, **0 of 12 local essays passed**, at roughly 20% per-quote fabrication — invented product
microcopy placed inside quotation marks. Short answers on the same model, same evidence and same
verifier pass fine; it is long-form that breaks down.

The essays are still generated, and then **retracted** — struck through under a banner naming the
fabricated quotes. That is not a bug to work around; it is the trust property doing its job on a
model that is too small for the task. A prompt-level mitigation was measured and reverted because
it moved the fabrication rate without changing a single verdict. Full method and numbers:
[docs/ship30-essays.md §10](docs/ship30-essays.md).

## Tests

Integration tests run against a **real PostgreSQL**, never SQLite — a substitute would not exercise
JSONB, the CASCADE, or the unique `(session_id, seq)` index that the concurrency guarantees rest
on.

### In the container (matches what ships)

```bash
docker compose --profile test build api-tests   # BUILD FIRST — `run` never rebuilds
docker compose --profile test run --rm api-tests
```

> ⚠️ **This build fails on a fresh clone, by design.** The `test` stage copies
> `data/transcripts/`, `spike/evidence/` and `spike/results/` as offline fixtures. All three are
> git-ignored: the first appears only after you ingest, and the other two are never in a clone.
> `docker compose up` (target `runtime`) copies none of them and is unaffected — so the app runs
> fine on a fresh clone even though this particular build does not.

### On the host

Requires a Python environment with `backend/requirements.txt` + `requirements-dev.txt` installed,
and a scratch database whose name contains `test` (the fixtures call `drop_all()`, and
`conftest.py` refuses to run otherwise).

```bash
cd backend
python -m pytest -q                                    # whole suite
python -m pytest tests/test_agent.py                   # one file
python -m pytest -k test_context_does_not_leak_between_sessions   # one test
```

**Read the skip count, not just the colour.** `corpus_ready`, `ollama_ready` and `pi_ready` skip
*loudly* when the corpus is not ingested or Ollama/Pi are absent — a green run full of skips is not
a pass. Expected: **401 passed / 1 skipped** on a Windows host (`signal.SIGKILL` does not exist
there; that test runs in the container), **396 passed / 6 skipped** in the container (packaging
tests reading files deliberately absent from the image).

### Manual test plan

25 UI and operational steps with their executed evidence:
**[docs/verification-matrix.md §7](docs/verification-matrix.md)**. That file is the status of
record for the whole project — one row per requirement, each backed by an executed test or a
performed manual step, including the requirements that are **not** met.

### Frontend

```bash
cd frontend && npm install && npm run build     # tsc -b — the only frontend gate
cd frontend && npm run dev                      # Vite on :5173, proxies /api to :8000
```

The Docker image builds its own frontend, so a fresh clone needs no npm step before
`docker compose up`. Note that `uvicorn` alone serves no SPA — the static mount exists only inside
the image — so a host-only dev loop needs Vite on `:5173`.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Every Ollama call stalls ~2 s | `localhost` resolves `::1` first; Ollama binds IPv4 only. Measured: **2032 ms vs 0.53 ms** per new connection | Use `OLLAMA_BASE_URL=http://127.0.0.1:11434` |
| Answers are always "the transcripts do not support this" | Ingestion never ran | `docker compose exec api python -m app.ingest`, then check `/api/retrieval/status` |
| `docker compose up` fails on the db port | Host 5432 is taken | Set `POSTGRES_PORT=5433` in `.env`, and keep the port in `DATABASE_URL` in sync |
| API unhealthy, Ollama fine | Container cannot reach the host | Docker Desktop supplies `host.docker.internal`. On **Linux**, also start Ollama with `OLLAMA_HOST=0.0.0.0` |
| Generation seems to hang, then VRAM spikes | `OLLAMA_CONTEXT_LENGTH` raised above 8192 on a small GPU | Restart `ollama serve` with `OLLAMA_CONTEXT_LENGTH=8192` |
| Container tests fail with missing fixtures | The `test` stage needs git-ignored fixtures | Expected on a fresh clone — see the warning above. Ingest first, or run the host suite |
| Container tests look unchanged after a code edit | `--profile test run` does **not** rebuild | `docker compose --profile test build api-tests` first |
| An essay appears struck through with a red banner | Grounding **failed** — the model fabricated a quote | Working as intended, and expected on the local 4B model. See the limitation above |
| A retrieval setting in `.env` has no effect in Docker | Compose does not forward the retrieval variables | Edit `docker-compose.yml` as well |
| Postgres refuses to start after an upgrade | Postgres 18 stores data in a version subdirectory | The volume must mount at `/var/lib/postgresql`, not `/var/lib/postgresql/data`. Named volume only — never a Windows bind mount |
| No answer, and logs mention `generation_timeout` | A turn exceeded the idle (120 s) or total (900 s) bound | Retry, or raise the bounds in `.env` **and** `docker-compose.yml` |

Logs are structured JSON and carry a `request_id` that correlates a failure to its access-log line:

```bash
docker compose logs -f api
```

## Project structure

```
backend/app/          FastAPI application (see architecture.md for the boundary chain)
  corpus/manifest.json    the pinned 20-episode corpus: source commit + per-episode sha256
  ingest/                 fetch → parse → chunk → embed
  prompts/                code-owned grounding rules (a skill cannot relax these)
  routers/                HTTP transport only
backend/tests/        401 tests against real PostgreSQL
backend/migrations/   Alembic; 4 revisions
frontend/src/         React + TypeScript; api.ts owns SSE, useChat.ts the state machine
.claude/skills/       6 hand-written skills; 05-ship30-writing is live prompt input
agent-transcripts/    how this was built, including what went wrong
docs/                 measurements and decisions, incl. the verification matrix
deploy/               Pi provider configuration, credential-free by construction
```
